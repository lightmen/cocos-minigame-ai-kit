# game-route — 选轨

**任何任务的第一步。** 先出选轨卡，再决定动不动手。用户只问「这个该怎么做」时，出卡后停下等确认。用户明确要动手时，Lite 直接改，Standard / Heavy 先进 `specs/`。

## 判定

从上往下，命中即停。**拿不准选更重的一档。**

### 是不是 Heavy？

命中任一即 Heavy：

- 引擎升级、渲染管线或物理方案变更
- 包体结构调整：新增/合并分包、主包裁剪、引擎分离、开放数据域
- 战斗同步方案变更（帧同步 ↔ 状态同步、回滚机制、预测逻辑）
- 客户端协议与服务端需要**同时**改（跨仓改动）

### 是不是 Standard？

命中任一即 Standard：

- 新增一个界面或一个玩法系统
- 对接新的协议消息（服务端已定义，客户端首次接入）
- 新增 Asset Bundle，或改变资源的 bundle 归属
- 新增本地存档字段 / 改变存档结构
- 新增需要策划口径的规则（数值公式、掉落、匹配规则）

### 否则 Lite

修 bug、调日志级别、改 UI 文案、数值微调、已有组件内小逻辑、动效与布局微调、性能小优化。

### 新玩法先有 GDD

判定结果是 Standard 或 Heavy，且这次是**新玩法或新的玩家循环**时，选轨卡的下一步是 `game-gdd`，不是写 spec。人确认 `specs/<NNN>-name/gdd.md` 之后，才更新 `feature.json` 并写 spec。

下面这些不是新玩法，不走 GDD：修 bug、改文案、调一个已有常量、给已有界面加一个已有规则里的按钮。

## 选轨卡格式

```
轨道：Standard
理由：新玩法，有需要策划确认的战斗循环
最低制品：人确认的 specs/003-raid/gdd.md，然后 spec + plan + tasks；更新 feature.json
下一步：game-gdd。GDD 确认前不写 spec、不写代码
升轨信号：若协议要和服务端一起改 → 升 Heavy，补 adr.md
编辑器验证：会改场景或预制体，收尾走 game-mcp
```

Lite 的卡同样这些列。`最低制品` 写「变更说明 + 验证步骤，不建 specs/」。不涉及场景和预制体时，`编辑器验证` 写「不涉及」。

## 出卡之后

| 轨道 | 走向 |
|-|-|
| Lite | 直接改代码 → `game-verify` → 场景/预制体再加 `game-mcp` |
| Standard | 新玩法先 `game-gdd` → 更新 `.specify/feature.json` → spec → plan → tasks → **按任务 ID 逐个实现** |
| Heavy | Standard 全流程 + 同目录 `adr.md` + 人做架构终审 |

## 升轨信号

动手过程中出现下面任一情况，**停下来重新出卡**：

- 本来只改逻辑，发现要加协议字段
- 本来只调数值，发现要加一列配置 / 加一张表
- 本来改一个界面，发现要抽一个新的公共 UI 基类
- 本来是客户端的事，发现服务端也得配合改
- 本来是修 bug，发现缺的是一整段还没设计过的玩法

## 禁止

- 对 Lite 任务创建 `specs/` 目录或写 spec 文档
- 跳过选轨直接改代码
- Standard / Heavy 不带任务 ID 就一次性实现整个功能
- 新玩法没有人确认的 GDD 就开始写 spec 或代码
