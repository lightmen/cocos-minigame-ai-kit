# Cocos 微信小游戏 · 客户端宪法

**版本 v1.0.0** · 适用范围：采用本模板的客户端代码与资源

宪法写的是**已经决定要执行的硬约束**。每一条都能在 Review 时二选一地判定：破了就打回。

Agent 把这里当硬边界，人把这里当合入标准。

---

## 一、包体与资源

### 原则 1 · 包体是第一约束

微信小游戏的硬上限是**主包 4MB、全部分包合计 30MB**。这是发布门槛。

任何新增资源的改动，必须在改动说明里写清三件事：落在哪个 bundle、预估体积增量、为什么不能放远程。

- `assets/resources/` 下的一切都会进主包。这个目录只允许放启动首屏必需的极小资源。
- 图集、音频、大贴图一律进 `assets/bundles/<name>/`，或走远程资源服务器。
- 新建 Asset Bundle 至少是 Standard 轨道。

**违反判定**：改动新增了 `assets/resources/` 下的非文本资源，且没有体积说明。

### 原则 2 · 资源必须显式释放

动态加载的资源和 Asset Bundle 要有明确的释放时机。界面关闭时释放其独占资源，bundle 用完调 `releaseAll` 或按引用计数释放。

**违反判定**：新增了 `loadBundle` / `load` 调用，但代码里找不到对应的释放路径。

## 二、分层

### 原则 3 · 战斗逻辑与引擎解耦

所有影响战斗结果的规则——伤害计算、状态机、技能判定、同步逻辑——放在 `assets/scripts/core/`。

**`core/` 禁止 `import { ... } from 'cc'`。** 它只依赖纯 TypeScript，因此可以脱离编辑器跑单测。

`assets/scripts/game/` 里的 Cocos Component 只做四件事：采集输入、调用 core、把 core 的结果渲染出来、管理生命周期。

**违反判定**：`core/` 里出现 `import 'cc'`；或战斗数值计算写在 Component 的 `update` 里。

### 原则 4 · 平台 API 走适配层

业务代码里禁止直接出现 `wx.`、`window`、`document`、`localStorage`、`XMLHttpRequest`。

微信平台能力统一封装在 `assets/scripts/platform/`，对外暴露 Promise 化接口，并且在非微信环境有可用的降级实现。

**违反判定**：`platform/` 以外的任何文件里出现 `wx.` 或 `window.`。

### 原则 5 · 节点引用用 @property

禁止 `find('Canvas/UI/HUD/ScoreLabel')` 这类路径字符串查找节点，也禁止 `getChildByName` 链式调用。

节点引用通过 `@property(Node)` / `@property(Label)` 在编辑器里拖，或者通过明确的组件查询拿到。

**违反判定**：新增代码里出现 `find(` 的路径字符串形式。

## 三、协议

### 原则 6 · 协议是跨仓契约，本仓只消费

协议定义由服务端仓维护。客户端同步后**不在本仓修改协议定义**。

生成物落在 `assets/scripts/net/generated/`，**禁止手改**。生成结果不对，就回服务端仓改源头再重新生成。

需要新增字段或消息号时，这是跨仓改动，按 Heavy 处理：先和服务端对齐，再同步。

**违反判定**：`net/generated/` 出现在 diff 里，但同一次改动没有伴随一次同步操作。

## 四、性能

### 原则 7 · 帧循环不产生垃圾

`update`、`lateUpdate` 以及被它们调用的整条链路里，禁止：new 对象、数组/对象字面量、字符串拼接、创建闭包、`Array.map/filter/forEach` 的临时分配。

需要的临时对象在初始化时预分配并复用。频繁创建销毁的节点（子弹、特效、飘字）走对象池。

**违反判定**：`update` 调用链里出现对象字面量或字符串模板。

---

## 五、工程

### 原则 8 · 生成目录不进版本库

`build/`、`library/`、`temp/`、`local/`、`profiles/`、`node_modules/` 一律 gitignore。

`assets/` 下每个资源的 `.meta` 文件**必须提交**。

**违反判定**：diff 里出现 `library/` 或 `temp/`；或新增资源没有带上对应的 `.meta`。

### 原则 9 · 每次改动必须有可执行验证

改完至少跑 `game-verify`：TypeScript 类型检查 + `core/` 单测。涉及资源或包体的改动追加 `game-build` 的包体检查。

改了场景、预制体，或玩家看得见的界面、动效、手感：必须走 `game-mcp`，在已经打开该工程的 Cocos Creator 里检查到。类型检查通过，不能代替这一步。

Lite 轨道如果没有新增 `core/` 规则，不强制新增测试文件，但仍然必须有可执行的验证步骤。

**"后续观察"、"应该没问题"、"逻辑上是对的" 都不是验证。**

**违反判定**：改动说明里没有任何一条别人能复现的命令或操作步骤。场景或预制体有改动，说明里却没有编辑器里的场景名、操作和预期结果。

### 原则 10 · Agent 不越界

- 禁止主动 `git commit` / `git push`，除非用户明确说了提交。
- 禁止顺手重构、顺手改格式、顺手修相邻的无关代码。发现了就单独提出来，让人决定要不要单独开一轨。
- 禁止为了让类型检查通过而写 `as any` 或 `@ts-ignore`。
- 禁止在用户没有点名时调用会删除节点、删除资源、或关掉 MCP 安全检查的编辑器工具。

## 六、新玩法开工

新玩法、新的玩家循环，在写 `spec.md` 之前必须有一份人确认过的 GDD。

- 用 Game Dev Studio 的 GDD 流程起草（见 `game-gdd`）。
- 确认后的文件放在 `specs/<NNN>-name/gdd.md`。
- `spec.md` 的规则口径引用这份 GDD。两边数字不一致时停下问人，不自行选一个。
- Game Dev Studio 只负责设计文档。Cocos 脚本、场景、协议仍按本仓库的任务 ID 实现。

修 bug、改文案、调一个已有常量，不写 GDD。

**违反判定**：新玩法的 `specs/` 目录里没有人确认过的 `gdd.md`，却已经有实现代码。

---

## Review 顺序

1. **轨道选对了吗** — Lite 却新增了协议字段或 bundle，直接打回。新玩法没有确认过的 GDD，直接打回。
2. **宪法破了吗** — 对照上面各条，尤其是分层（3/4）、生成物（6/8）、场景验证（9）。
3. **Standard / Heavy 的 plan 是否可执行** — 有没有写清验证手段，`core/` 单测覆盖了没有，场景改动有没有编辑器步骤。
4. **业务与手感是否正确** — 这一层必须人看。

## 修订

宪法的修改本身至少是 Standard 轨道：改动要说明为什么现有原则不再适用，并同步更新 `AGENTS.md` 和相关 Cursor rules。版本号按语义化递增。
